## 0. 가장 아픈 질문 5 — 리허설 문장 포함

### Q1. 전부 가상 데이터 아니냐. 실제 공정에서 되는지 모르지 않나. (심사평 01·03·04·05·06·07 — 6인 공통)

- **한 줄 답**: 맞다, 전부 가상 데이터다. 우리가 먼저 밝힌다. 가상에서 증명한 것은 「성능」이 아니라 「구조와 검증 규율」이고, 실제 데이터 성능은 파일럿에서 잰다.
- **근거**: 가상 데이터 · 정답지도 우리가 만듦 · 실데이터에서 낮아질 수 있음 = 공식수치 「쓸 때 반드시 함께 밝힐 것」 1~3 / 채점이 헐겁지 않다는 근거: 정답지 60분 이동 시 100% → 75%(공식수치 같은 절 2 · scenarios 「변칙 재검증」) / 정답지 자체를 24종 전수 파형 대조해 2종 정정, 재채점 무변동(scenarios 「정답지 자체를 파형과 대조했다」) / 결함 없는 정상 14근무 이벤트 0(공식수치 ③) / 심사평이 「검증 규율」을 칭찬(심사평 03·04·05·06 기대되는 점).
- **말하면 안 되는 것**: 「실제 데이터에서도 100% 나올 것」 · 「가상이지만 실제와 같다」.
- **리허설**: 「네, 데이터는 전부 가상이고 정답지도 저희가 만들었습니다. 그래서 저희가 증명한 것은 성능 숫자가 아니라 두 가지입니다. 하나는 채점이 저희에게 유리하지 않다는 것 — 정답지를 60분만 옮겨도 100%가 75%로 무너지고, 이상을 하나도 넣지 않은 14근무에서는 이벤트가 0건입니다. 다른 하나는 구조 — 공정이 전혀 다른 수처리 플랜트에 검출 코드 0줄 수정으로 올라갔습니다. 실제 데이터에서 성능이 얼마인지는 파일럿에서 Read-only 섀도 모드로 재는 것이 첫 일이고, 그 지표를 이미 정해 두었습니다.」

### Q2. 채택률도 없는데 왜 믿나. 스스로 정한 성공 조건(50%)을 한 번도 시험하지 않았다. (심사평 03·04·05·06·07)

- **한 줄 답**: 본선까지는 미측정이 맞다. 결선에서 첫 실측치를 만들었다 — `[값 대기]` — 표본은 작고 팀원(+현장 운전원 N명) 것이라 「첫 값」으로만 말한다.
- **근거**: 본선 시점 미측정 = 검증정리 5장 다섯째 · 기획서 6-2 「채택률 측정 미측정」 / 채택률은 정확도 지표가 아니라 감도 조정 지표로 설계(기획서 5-1 「채택률 50%」 설명) / 결선 측정 = 심사평 §4 받는 것 2(도영, 승인 화면 그대로) → **`[값 대기]` 항목 수·채택 수·제외 사유 목록 → `docs/공식수치.md`**.
- **말하면 안 되는 것**: 「50% 달성」 · 「채택률 N%」를 표본 크기 없이 · 팀원이 누른 값을 「현장 운전원 값」으로.
- **리허설**: 「본선 자료에 미측정이라고 적은 그대로입니다. 결선 이틀 동안 완성된 근무 초안을 항목 단위로 채택·제외·사유를 표시받아 첫 값을 만들었습니다 — [항목 N개 중 채택 M개, 제외 사유 K종]. 표본이 [근무 수·사람 수]라 이건 통계가 아니라 첫 점 하나입니다. 이 값보다 중요하게 본 것은 제외 사유 목록입니다 — 무엇을 왜 빼는지가 다음 감도 조정의 재료가 되기 때문입니다.」

### Q3. 정비·운전모드 전환·센서 불량에서 오검출이 쏟아지면? 정지 때 초안이 39건까지 늘던데. (심사평 05·04)

- **한 줄 답**: 정지·Trip 은 이미 「플랜트를 정지하셨습니까?」 확인 질문 하나로 접는다. 단독 계측 이상은 결선에서 AI 프롬프트로 「계측·격리·정비 의심」 판정을 붙일 수 있는지 가상 데이터로 시험했다 — `[값 대기]`. 실데이터 운전모드별 오검출은 파일럿 지표다.
- **근거**: 정지 감지 문턱 = 10분 창 안 동시 이탈 30% — Trip 90.6% · 계획정지 69.8% vs 이상 12종 7.5%, 두 무리 사이 62%p(scenarios 「완화됨 — 플랜트 정지 시 초안 폭주」) / 엔진 무수정, `app/ports.py` 에만 얹음 · 회귀 4건(같은 절) / 39항목은 초기 추정이었고 5일 실측 압축비(약 4:1)로 「약 10개」로 정정(scenarios 「알려진 한계」 표) / first-out K-201 0초·2초 일치(scenarios 「강제 주입 2근무 실측」) / 수처리 이식에서 간헐 운전 태그(JI-401·CI-906·PSH-01)는 고착 오탐이 나 태그를 빼서 우회 — 운전모드 플래그는 남은 과제(수처리 Q10·7장) / 단독 이상 AI 판정 = 심사평 §4 받는 것 4 → **`[값 대기]` probe-isolated 결과, 가상 데이터, `prod 미확인`**.
- **말하면 안 되는 것**: 「운전모드를 자동 인식한다」 · 「정비 중 오검출 0」 · 실데이터에서 확인했다는 뉘앙스.
- **리허설**: 「정지와 Trip 은 본선 때 실측해서 알고 있던 약점입니다. 지금은 10분 안에 태그 30% 이상이 한꺼번에 벗어나면 초안 맨 앞에 「플랜트를 정지하셨습니까?」 한 항목을 세우고, 계획 정지인지 Trip 인지 계측 장애인지는 사람이 답하게 합니다 — 데이터만으로는 갈 수 없고, 틀리게 묶으면 되돌릴 수 없어서요. 한 점만 고착·이탈하고 연결 태그는 정상인 「단독 이상」은 결선에서 AI 판정으로 계측·정비 의심을 붙이는 시험을 했고 [결과]. 다만 이건 가상 데이터라, 실제 정비·모드 전환에서 오검출이 몇 건인지는 파일럿에서 운전모드별로 따로 세는 지표로 잡아 두었습니다.」

### Q4. AI 초안이 잘 나오면 사람이 자기 확인·조치를 안 기록하게 되지 않나. 책임이 약해진다. (심사평 08)

- **한 줄 답**: 그 지적을 받아 결선에서 채택 시 **완료 / 진행중** 둘 중 하나를 고르지 않으면 승인이 안 되게 했고(서버에서 막는다 · 기본값 없음), 진행중 항목은 다음 근무 초안 맨 위에 접힌 「이월 항목 N건」 묶음으로 본문 항목과 따로 보이며 완료로 닫을 때까지 남는다.
- **근거**: 설계 = 심사평 §4 받는 것 3(기본값 없음 → 일괄 수락 방지 · 이월) — 상태는 팀장 결정으로 **완료 / 진행중 두 개**로 고정, 채택 항목에 상태가 없으면 서버가 승인을 거부, 진행중은 다음 근무 초안 맨 위 접힌 「이월 항목 N건」 묶음(본문 항목과 분리)으로 완료로 닫을 때까지 유지 → **`[값 대기]` 구현·화면 확인, final/status-switch** / **`[구현 대기: 이월 항목을 초안·프롬프트에 붙이는 훅 — final/carry-hook 예정]`** / 이미 있던 장치: AI 는 조치 문장을 쓰지 않음, 조치는 확정 일지 문장만 인용(기획서 3-5 표 「기록 작성하기」) · 없는 조치 지어냄 0건(공식수치 ⑤) / 「무시해도 됨」 코멘트를 조치로 인정하지 않음 — 침묵 사고 시험 2·3차 방어(scenarios 「침묵 사고 시험」) / 확정된 것만 회수, 제외 코멘트는 쌓이지 않음(scenarios 「반복 시험」 ②) / 표준이 요구하는 「진행 중 작업·다음 할 일」은 ENGRA 가 기록 자리만 주는 항목(한장 ④ 커버리지: 자리만 4).
- **말하면 안 되는 것**: 「AI 가 조치를 제안한다」 · 「기록 책임 문제는 없다」 · 「추천 조치」 칸이 안전하다고(과거 일지 원문이 그대로 통과 — scenarios 「화면은 막히지 않는다」).
- **리허설**: 「이 지적이 결선에서 저희가 고른 문제 중 하나입니다. AI 는 원래 조치 문장을 쓰지 않고, 과거 일지에 사람이 남긴 조치만 인용합니다. 여기에 결선에서 더한 것은 상태 스위치입니다 — 채택한 항목마다 완료·진행중을 직접 고르지 않으면 승인되지 않습니다. 기본값이 없고 서버에서 막아서, 모두 한 번에 넘기는 습관을 끊습니다. 진행중 항목은 다음 근무 초안 맨 위에 「이월 항목 N건」 접힌 묶음으로 본문과 따로 이어져 완료로 닫을 때까지 남습니다. AI 가 잘 쓸수록 사람 기록이 사라진다는 걱정을, 사람 기록이 없으면 닫히지 않는 구조로 뒤집었습니다.」
- **후속 질문 대비**: 「이월이 쌓이면 초안이 지저분해지지 않나?」 → 접힌 「이월 항목 N건」 묶음으로 본문과 따로 둔다 — 펼쳐야 보이고, 완료로 닫으면 다음 근무 초안에서 사라진다.

### Q5. 1,000태그, 억 단위 점수의 실제 설비에서도 되나. 53태그로만 잰 것 아닌가. (심사평 05·07 「대량 데이터」)

- **한 줄 답**: 태그를 16배(848점)로 늘려 실측했다 — 검출 108초, 증가는 n^1.3, 제약은 CPU 가 아니라 메모리다. 1,000 이상은 재지 않았다.
- **근거**: 53→848태그 2.8초→108.3초, 태그당 53.6→127.8ms(scenarios 「태그를 16배로 늘려도 검출은 108초다」) / 이유: 상관 검출기가 전수 조합(1,378쌍) 아닌 태그 마스터 링크 29쌍만 봄(같은 절) / 메모리 848태그 ≈146MB, 서버 MemoryMax 700MB(같은 절) / 50일 100근무 연속: DB 7근무째부터 평평, 검출 평균 18.3초 누적 저하 없음(공식수치 ④) / 운영 조건: 근무당 1회 배치, 교대 60분 전 생성(기획서 5-1) / 규모 의존 수치를 발표에서 뺀 이유(속도논리 §1).
- **말하면 안 되는 것**: 「114만 점 5.4초」를 강점으로 · 「선형으로 는다」 · 「1,000태그도 된다」(미측정).
- **리허설**: 「53태그만으로 말하면 안 된다고 생각해서 태그 마스터를 복제해 848점까지 늘려 재봤습니다. 검출은 108초, 16배에 39배라 대략 n의 1.3제곱입니다 — 제곱이 아닌 이유는 상관 검출이 전수 조합이 아니라 태그 마스터에 적힌 연결 쌍만 보기 때문입니다. 근무당 한 번, 교대 60분 전에 도는 배치라 2분은 여유입니다. 다만 두 가지는 정직하게 말씀드립니다. 늘려야 하는 것은 CPU 가 아니라 메모리이고, 1,000태그 이상은 재지 않았습니다. 억 단위 포인트라면 파일럿에서 메모리 상한부터 재야 합니다.」

## 1. 심사평 직결 — 「아쉬운 점·보완할 점」에서 온 질문

### Q6. 초안 생성이 5분 목표를 넘던데(6.5~7.2분), 결선에서 줄였나? 전후를 같은 데이터로 비교했나? (심사평 01·05·06·07)

- **한 줄 답**: 5항목 묶음 순차 호출을 항목별 병렬 호출 + 연속성 판정 1회로 바꾸고, 같은 근무 데이터로 전후를 재서 남긴다 — `[값 대기]`.
- **근거**: 본선 값: 13~16항목 6.5~7.2분(387~435초) · 라이브 8항목 3분 23초 · 6항목 3분 10초(기획서 3-5 · 대장 E2) / 5분 = 교대 1시간 전 생성의 10%(기획서 5-1) / 병렬화 방식과 「같은 근무 데이터로 전후 실측」 = 심사평 §4 받는 것 1 → **`[구현 대기: 항목별 병렬 호출 + 연속성 판정 1회 — final/speed-parallel]`** · **`[값 대기]` 전·후 분:초, 항목 수, 근무 id → `docs/공식수치.md`**.

## 3. AI 네이티브 — AI 가 중심에 있나

### Q19. AI 를 빼면 무엇이 안 되나? 통계 검출만으로 되는 것 아닌가? (초안 Q2)

- **근거**: 6단계 표(기획서 3-5) / AI 켬·끔 대조: 태그·근거·출처 필드는 동일, 문장과 판단만 달라짐(기획서 3-5 「불변 조건」) / 7근무 실측: 사례 50건 중 채택 33·기각 17, 중요도 재판정 10/52(19%), 사유 31/31(공식수치 ⑤) / 폴백 없음(기획서 3-5 「AI 는 필수」 · 심사평 03 기대되는 점).

### Q20. AI 가 하는 게 문장 쓰기뿐이면 템플릿과 무엇이 다른가? (초안 Q10·Q11)

- **말하면 안 되는 것**: 「경쟁자가 없다」.

### Q41. 실패 시나리오와 리스크는? 무엇이 이 프로젝트를 죽이나?

- **한 줄 답**: 셋이다. ① 실데이터에서 오검출이 많아 근무자가 안 믿는 것 — 섀도 모드로 먼저 잰다. ② AI 초안이 사람 기록 책임을 약화시키는 것(심사평 08) — 기본값 없는 상태 스위치와 이월로 대응했다. ③ 「무시해도 됨」 같은 선의의 틀린 코멘트가 순환하는 것 — AI 는 방어됐지만 「추천 조치」 화면은 아직 원문 통과다.
- **근거**: 심사평 05 보완할 점 / 심사평 §4 받는 것 3 → **`[값 대기]` 구현 확인** / scenarios 「침묵 사고 시험」·「화면은 막히지 않는다」.
- **말하면 안 되는 것**: 「리스크 없다」 · 사고 감소율.

### Q42. 파일럿 계획과 성공 지표는?

- **한 줄 답**: 실제 사업장 1개 근무조, 실제 RTDB Read-only 연결로 몇 주 섀도 모드 — 기존 인계는 그대로 두고 ENGRA 항목을 사후 채택·제외. 지표는 채택률·제외 사유·작성 시간 `전 − 후`(분/근무)·누락 건수·운전모드별 오검출·알람 기준 대비 선행 검출.
- **근거**: 기획서 6-4(1개 근무조 · RTDB 기간 지정 조회) / 심사평 05 보완할 점(Read-only 섀도 모드) / 시간 지표 정의(지표표 5절 2-나) / 알람 기준 대조군(속도논리 §3 — 네 조건 충족) → **`[값 대기]` 알람 대비 비율(① 세트 분모 정리 후 `docs/공식수치.md`)**.
- **말하면 안 되는 것**: 목표 수치를 「달성할 것」으로 · 「현장에서 알람 미발생 이상 61%」(시나리오 구성에 달린 값 — 속도논리 §3).

### Q43. 알람 시스템을 고도화하면 되는 것 아닌가? 범용 이상감지 제품과 무엇이 다른가?

- **한 줄 답**: 알람은 한계값을 넘을 때 울린다. ENGRA 는 알람을 대체하지 않고 12시간을 다시 훑어 한계값을 넘지 않은 변화(드리프트·고착·상관 붕괴)를 다음 근무에 전달하는 별도 계층이다. 범용 이상감지와 다른 점은 산출물이 「인계 초안 → 사람 승인 → 다음 근무에 과거 조치로 회수」 순환이고, AI 가 조치를 쓰지 않는다는 것이다.
- **근거**: 심사평 05 기대되는 점(알람 대체하지 않는 별도 계층) / 알람 선행 검출 현재 코드 7/10·16/18, 최대 +616·+560분(대장 E9 — 공식수치 갱신 대기) / 단일 태그로 절대 안 잡히는 상관 붕괴 `#11`(scenarios 시나리오 표) / Texas City 「redundant high level alarm did not activate」 · Toledo 12시간 알람 3,712건(속도논리 §3 · 대장 A2·A3) / ENGRA 는 알람 로그를 읽지 않음(대장 E4).
- **말하면 안 되는 것**: 「알람이 울리지 않은 이상」 · 「알람 폭주 해결」을 기능으로(알람 이력 입력 없음 — 지표표 6절).

### Q44. 시간 절감·사고 감소를 돈으로 환산하면?

- **한 줄 답**: 못 한다, 하지 않는다. 분자(작성 시간 단축·누락 감소)가 미측정이라 연간·금액 환산 근거가 없다(심사평 04 도 그렇게 적었다). 파일럿 `전 − 후` 가 나오면 그때 계산한다.
- **근거**: 심사평 04 아쉬운 점 / 지표표 5절 2·3 / 한장 ⑤.
- **말하면 안 되는 것**: 「N% 절감 × 인원 × 시급」 · 사고 감소율.
