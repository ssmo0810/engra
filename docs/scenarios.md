# 특이 시나리오 정의

ENGRA가 감지해야 할 특이사항의 유형과 발생 조건을 정의합니다.
여기서 정의한 시나리오가 모의 데이터 생성기의 입력이 되고, 감지 성능(포함률) 측정의 기준이 됩니다.

- 담당: 임도영
- 목표: 15종 내외
- 주의: **실제 설비 태그명과 실제 운전 수치는 쓰지 않습니다.** 태그는 `AI-1201` 같은 가상 표기를 사용하고, 수치는 형태만 실제와 유사하게 잡습니다.

---

## 작성 방법

아래 표에 한 줄씩 채우면 됩니다. 모르는 칸은 비워두고 나중에 채워도 됩니다.

| 항목 | 설명 | 예시 |
| --- | --- | --- |
| 유형 | 어떤 종류의 이상인가 | 헌팅 / 드리프트 / 과압 / 과온 / 저온 / 임계 근접 / 연속 발생 |
| 대상 | 어떤 설비·계통에서 나타나는가 | 제품 순도, 압축기 토출온도, 밸브 개도 |
| 형태 | 값이 어떻게 움직이는가 | 30분간 진동 후 안정 / 2시간에 걸쳐 완만히 상승 |
| 크기 | 평소 대비 얼마나 벗어나는가 | 평소 변동폭의 4배 / 시간당 0.9℃ |
| 지속 | 얼마나 오래 가는가 | 29분 / 근무 내내 |
| 중요도 | 인수인계 관점에서 | 상 / 중 / 하 |
| 판단 근거 | 왜 그 중요도인가 | 알람에 안 걸리지만 재발 시 설비 손상 우려 |

`대상` 칸은 **가상 태그번호와 설명을 함께** 적습니다. 시나리오가 모의 데이터 생성기와 검출 알고리즘에 그대로 연결되도록 하기 위한 것입니다.
태그 정의는 [`tag_master.csv`](tag_master.csv) (계측 태그 53점), 배치는 [모의 DCS Overview 화면](asu_dcs_overview.html)에 있습니다.

> **4번 참고** — 원래 예시는 "냉각수 입구온도"였는데 태그 마스터에 냉각수 계통이 없어 `TI-401`(Main HX 인입 Air 온도)로 대체했습니다. 냉각수 태그가 필요하면 태그 마스터에 추가하겠습니다.
>
> **1번 참고** — 진폭 6배(±0.42%p)로 최저값이 99.18%가 되면서, `AI-707`의 L 알람을 **99.2% → 99.0%** 로 조정했습니다(태그 마스터 반영 완료). 알람선이 정상범위 하한(99.0%)과 일치하게 되어, **정상범위를 벗어나는 순간 알람**이라는 기준으로 정리됩니다. 이 시나리오는 여유 0.18%p를 두고 알람 미발생입니다.

**알람 미발생 13종 + 알람 발생 2종(6·10번)으로 구성했습니다.** 두 경로를 모두 시험하기 위한 것입니다.

- **알람 미발생 13종** — ENGRA의 핵심 가치. 알람에 안 걸리고 조용히 지나가는 신호를 잡아내는지 봅니다.
- **알람 발생 2종** — 알람이 울린 건도 인수인계장에 들어가야 합니다. 근무자가 이미 아는 사건이라도 **적는 걸 잊으면 똑같이 누락**입니다. 또한 두 건 모두 **알람이 울리기 한참 전부터 징후가 보이므로**, ENGRA가 알람보다 먼저 잡아내는지가 판정 기준입니다.

6·10번은 시나리오 자체가 알람을 만든 게 아니라, **연동 태그의 기여가 더해지면서 결과적으로 한계를 넘은** 경우입니다. 실제 공정에서 이상이 커지는 방식과 같습니다.

탐지 알고리즘 대응 (정기영님 `engine/` 참고용)

| 알고리즘 | 대응 시나리오 |
| --- | --- |
| Modified z-score (median/MAD) | 1, 4, 10, 12, 14 — 단일 시점 이탈 |
| CUSUM / EWMA | 2, 6, 9, 15 — 누적 추세 이탈 |
| 이동 표준편차 · 진폭 추세 | 3, 5, 13 — 진동 크기와 반복 횟수 |
| 태그 간 상관 추적 | 5, 8, 11, 15 — 조합으로만 보이는 신호 |
| 값 정체 감시 (stuck) | 7 — 변화량이 0에 가까운 상태 지속 |

> **전처리 주의 (12번)** — 999 ppm 같은 이상값이 그대로 통계에 들어가면 median/MAD와 이동 표준편차를 오염시켜 **다른 시나리오의 탐지까지 망가집니다.** 스파이크는 탐지 대상으로 기록하되 기준선 계산에서는 제외해야 합니다. 통합테스트에서 반드시 확인할 항목입니다.

## 채우면서 함께 봐 주실 것

- 이 유형은 **DCS 알람으로 잡히는가, 안 잡히는가?** — ENGRA의 핵심 가치는 알람에 안 걸리는 신호를 잡는 것입니다.
- 실제로 인수인계에 **적을 만한 가치가 있는가?** — 감지는 되는데 아무도 안 적는 항목이면 오탐입니다.
- 같은 현상을 두고 **근무자마다 판단이 갈릴 만한가?** — 갈린다면 그 자체가 우리가 해결하려는 문제의 사례입니다.

## 시나리오 주입 데이터 생성

[`asu_dcs_overview.html`](asu_dcs_overview.html)의 **SCENARIO INJECT** 탭에서 만듭니다.

**절차** — seed·시작일시 지정 → 랜덤 2~3종(또는 직접 선택) → `시나리오 주입 & 생성` → 24시간 데이터 생성 → 파일 내보내기

**생성 방식**
1. 태그 53점의 24시간 정상 베이스라인을 만듭니다 (기저값 + 드리프트 + 노이즈)
2. 고른 시나리오를 랜덤 시간대에 주입합니다 — **같은 태그가 겹치지 않게** 하고 시나리오 간 최소 30분 간격을 둡니다
3. 태그 간 연동을 적용해 **주입한 변화가 다른 태그로 전파**되게 합니다
4. 값 고정·스파이크처럼 전파되면 안 되는 것은 연동 후에 덮어씁니다

**내보내기** — `app/README.md` 연결 규약을 따릅니다.

| 파일 | 내용 |
| --- | --- |
| `asu_shift_day_12h.csv` | 주간 12시간 · `timestamp,tag,value` · 2초 주기 |
| `asu_shift_night_12h.csv` | 야간 12시간 · 같은 형식 |
| `asu_answer_key.json` | **정답지** — 주입한 시나리오 ID·태그·시작·종료·근무 구분 |

정답지를 **별도 파일로 분리**한 이유는, 데이터 파일에 정답이 섞이면 검출 엔진이 그걸 보고 맞힐 수 있어 성능 측정이 무의미해지기 때문입니다.

**재현성** — seed가 같으면 베이스라인·시나리오 선택·시간대 배치가 모두 동일하게 재현됩니다.

> 파일 저장은 GitHub Pages 주소에서만 됩니다. 아티팩트 미리보기 화면은 브라우저가 다운로드를 차단합니다.
