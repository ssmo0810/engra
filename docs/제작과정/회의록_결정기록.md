## #2 [요청] 검출 전처리 — 순간 스파이크가 기준선을 오염시키지 않도록
제기 ssmo0810 · 담당 giyeong2 · 2026-08-15 · **진행 중**

> 임도영님이 시나리오 정의 중 발견한 사항입니다. 검출 알고리즘 설계에 반영이 필요합니다.
>
> ## 문제
> 12번 시나리오는 분석기 순간 스파이크입니다 — `MI-804` 값이 0.5 ppm에서 **999 ppm으로 3초간 폭등 후 원복**합니다 (정상값의 약 2,000배).
>
> 이 값이 그대로 통계에 들어가면 median/MAD와 이동 표준편차가 오염됩니다. 그러면 **12번뿐 아니라 같은 구간의 다른 시나리오 탐지까지 망가집니다.**
>
> ## 필요한 처리
> - 스파이크는 **탐지 대상으로는 기록**하되 (12번 자체가 잡혀야 함)
> - **기준선(median/MAD·이동 표준편차) 계산에서는 제외**
>
> 두 가지를 동시에 만족해야 합니다. 단순히 이상값을 버리면 12번을 못 잡고, 그대로 쓰면 다른 걸 망칩니다.
>
> ## 참고
> - 시나리오 정의: `docs/scenarios.md` (12번, 그리고 하단 '전처리 주의' 항목)
> - 알고리즘 설계: `engine/README.md`
> - 통합테스트에서 반드시 확인할 항목으로 잡혀 있습니다.

## #3 [결정] 시나리오별 현장 조치 사항 — 어디에 쓸 것인가
제기 ssmo0810 · 담당 dylim404 · 2026-08-15 · **처리 완료**

> 임도영님이 `docs/scenarios.md` 다음 작업에 올려주신 항목에 대한 정리입니다.
>
> ## 논점
> '각 시나리오의 현장 조치 사항'을 시나리오 문서에 적을 필요가 있는가?
>
> 실제 운영에서 조치 내용은 **근무자가 승인 화면에서 코멘트로 직접 입력**합니다. 미리 정해둘 성질이 아닙니다.
>
> ## 다만 한 가지 용도가 있습니다
> ENGRA에는 **과거 조치 추천** 기능이 있습니다 — 같은 태그·유사 증상의 과거 사례를 찾아 그때의 조치를 코멘트로 제안하는 것입니다. 데모 화면의 `과거 조치 추천 — 2026-06-12 야간조: 샘플링 의뢰 후 정상 확인` 이 그것입니다.
>
> 이 기능이 동작하려면 **과거 확정 일지에 조치 문구가 들어 있어야** 합니다. 즉 시연용 과거 일지를 만들 재료가 필요합니다.
>
> ## 제안
> - 시나리오 표에 조치 열을 넣되, 용도를 **'모의 과거 일지 시드'** 로 명확히 한다
> - 시나리오 1건당 조치 문구 1~2개면 충분 (실제 근무자가 쓸 법한 한 문장)
> - 우선순위는 낮음 — 20종 확장(#1)이 끝난 뒤
>
> ## 의견 주실 것
> - 이 용도로 필요하다고 보시는지
> - 아니면 과거 일지는 나중에 별도로 만들지

**논의와 결론**

- *dylim404* (2026-08-25) — **넣는 것으로 정했습니다.** 용도는 말씀하신 대로 **모의 과거 일지 시드** 하나입니다. 커밋 `9784b71`. ## 왜 필요한지 확인했습니다 ENGRA 의 과거 조치 추천(초안 파란 칸)은 **과거 확정 일지에 조치 문구가 있어야** 동작합니다. 그런데 시연 첫 화면에는 과거가 없어 빈칸이 됩니다. 파란 칸이 ENGRA 의 핵심 차별점인데, 그걸 보여주려면 근무를 2개 연달아 돌리고 1근무에서 사람이 코멘트를 타이핑해야 합니다. **5분 영상에서는 어렵습니다.** 미리 심어두면 첫 화면부터 채워집니다. 그것 하나를 위한 것이고, **실제 운영의 조치는 근무자가 승인 화면에서 직접 입력한다**는 판단은 그대로 유지했습니다. ## 넣은 위치 `docs/scenarios.md` 에 **별도 표**로 넣었

## #4 [요청] engine/api.py — 검출 엔진 붙일 자리가 준비됐습니다
제기 ssmo0810 · 담당 giyeong2 · 2026-08-23 · **처리 완료**

> **누구에게** — 정기영 (`engine/`)
>
> **무엇이 필요한가**
>
> `engine/api.py` 에 아래 네 함수를 만들어 주세요. 파일 이름과 함수 이름이 이대로면 **자동으로 연결됩니다.** 제 코드는 손댈 필요가 없습니다.
>
> ```python
> summarize(series)                       -> {태그: 요약}
> build_baseline(summaries)               -> {태그: 기준선}
> detect(series, baselines)               -> [이벤트, ...]
> compose(shift, events, find_precedents) -> [초안항목, ...]
> ```
>
> **시작하는 법**
>
> `app/stub_engine.py` 를 열면 네 함수가 전부 동작하는 상태로 들어 있습니다. **그대로 복사해서 `engine/api.py` 로 옮기고 내용만 채우시면 됩니다.** 형식 고민은 안 하셔도 됩니다.
>
> 돌려보는 것도 한 줄입니다. 설치할 것 없습니다.
>
> ```bash

>
> `engine/api.py` 가 있으면 실행 첫 줄에 `엔진: engine`, 없으면 `엔진: stub` 이 찍힙니다. 이걸로 내 코드가 실제로 붙었는지 바로 확인됩니다.
>
> **형식이 어긋나면 그 자리에서 멈춥니다**
>
> 일부러 그렇게 만들었습니다. 예를 들어 severity 에 `"HIGH"` 를 넣으면 이렇게 나옵니다.
>
> ```
> 이벤트 0(TI-1): severity 는 상/중/하 중 하나여야 합니다. 받은 것: 'HIGH'
> ```
>
> 조용히 넘어갔다가 통합할 때 발견하는 것보다 낫습니다.
>
> **왜 필요한가**
>
> 지금 임시 엔진은 **알람 한계선(LL/L/H/HH)을 넘었는지만** 봅니다. 헌팅·드리프트·상관 붕괴·값 고착은 하나도 못 잡습니다.
>

>
> **우선순위**
>
> 1주 차에는 `summarize` · `build_baseline` · `detect` 셋만 있으면 됩니다. `compose` 는 임시 문장 틀이 돌고 있어서 2주 차로 미뤄도 통합에 지장 없습니다.
>
> `detect` 도 전부 한 번에 하실 필요 없습니다. **modified z-score(단일 시점 이탈) 하나만 들어와도** 통합이 시작됩니다. 거기서부터 CUSUM·이동 표준편차·상관 추적을 붙여 가면 됩니다.

>

## #7 [요청] 데이터 생성기 — 순도 태그에 대칭 진동을 걸면 100% 를 넘습니다
제기 ssmo0810 · 담당 dylim404 · 2026-08-24 · **처리 완료**

> **누구에게** — 임도영 (`docs/`)
>
> **무엇이 필요한가**
>
> `osc()` 가 진폭을 대칭으로 더하는데 클램프가 없어서, 순도 태그에 물리적으로 불가능한 값이 생성됩니다.
>
> ```js
> function osc(D,tag,s,e,amp,period,decay){
>   D[tag][i] += amp*(...)*Math.sin(...)   // 상한 검사 없음
> }
> ```
>
> 시나리오 1은 `AI-707` 에 amp 0.42 를 겁니다. 기저값이 99.6 이므로 상향 진동에서 **99.6 + 0.42 = 100.02%** 가 나옵니다. 산소 순도가 100% 를 넘을 수는 없습니다.
>
> **왜 필요한가**
>
> 이 CSV 가 두 곳으로 갑니다.
>
> 1. 정기영님 검출 엔진 입력 — 불가능한 값이 기준선을 오염시킵니다 (#2 와 같은 종류의 문제)

>
> **제안**
>
> `osc()` 에 태그 마스터의 `normal_lo`/`normal_hi` 로 클램프를 걸거나, 순도처럼 상한이 물리적으로 막힌 태그는 **하향 편향 진동**으로 처리하는 방법이 있습니다.
>
> 참고로 데모 차트에서 같은 문제를 만나 이렇게 처리했습니다 — 중심을 99.45 로 두어 최저 99.18(시나리오 값 그대로)·최고 99.72(정상 상한 99.9 안)로 맞췄습니다. 시나리오 표의 `±0.42%p` 표기도 **하향 0.42** 로 읽는 것이 맞아 보입니다(최저 99.18 과 일치).

## #9 [결정] 초안 생성 LLM 을 어떻게 붙일까 — API 키 vs CLI 서브프로세스
제기 ssmo0810 · 담당 ssmo0810 · 2026-08-25 · **진행 중**

> ## 무엇을 정하는가
>
> `app/ports.py` 의 `compose()` 는 지금 문장 틀로 동작합니다. 여기에 LLM 을 붙이는 방법이 두 가지입니다.
>
> - **A. API 키 방식** — `anthropic` SDK 를 설치하고 API 키로 호출
> - **B. CLI 서브프로세스 방식** — `claude` / `codex` 실행 파일을 `subprocess` 로 호출, 구독 계정 사용
>
> ## 결론 — B (CLI 서브프로세스)
>
> ### 선례가 이미 있다
>
> `cs-study-lms` 가 같은 문제를 B 로 풀어 운영 중입니다 (`scripts/auto-evaluate.js`).
>
> ```
> codex exec --ephemeral --ignore-user-config --sandbox read-only
>            --output-schema evaluation-result.schema.json
>            --output-last-message result.json --cd <workDir>
> ```
>
> 프롬프트는 stdin, `spawnSync`, 타임아웃 10분, 버퍼 50MB. `EVALUATOR_PROVIDER` 환경변수로 `claude -p --tools Read` 경로와 갈아끼웁니다. **API 키가 코드 어디에도 없습니다.** 재시도 지연(`RETRY_DELAYS_MS`)과 잠금 파일까지 붙어 있어, 서브프로세스 LLM 호출에 필요한 것이 무엇인지도 이미 학습돼 있습니다.
>
> ### ENGRA 에 B 가 맞는 이유
>
> **① 기획서의 "외부 의존 0" 주장을 지킨다.** 기획서 4-3 에 "`app/`·`tools/` 의 모든 import 가 파이썬 표준 라이브러리, 의존성 선언 파일 없음"을 실측으로 적었습니다. `anthropic` SDK 를 넣으면 이 문장이 거짓이 되고, Ground Rule 의 **오픈소스 라이선스 준수·출처 명시** 의무도 새로 생깁니다. `subprocess` 는 표준 라이브러리입니다.
>
> **② 비용 0.** 대회가 Claude Max 계정을 1인당 1개월 제공합니다. API 비용 지원(팀당 최대 5만원)은 **사용량·금액 실비 인증**이 조건이라 캡처와 정산이 따라붙습니다. 안 쓰면 되는 일입니다.
>
> **③ 실배포 이식 경로가 A.Biz 다.** 사내는 폐쇄망이라 최종적으로 A.Biz 어댑터로 가야 합니다. API SDK 를 박으면 나중에 **걷어내는** 작업이 추가됩니다. `compose()` 하나만 교체하는 구조면 CLI든 A.Biz든 같은 자리입니다.
>
> **④ 구조화 출력이 API 못지않다.** `--output-schema` 로 JSON 스키마를 강제할 수 있습니다. 추정이 아니라 cs-study-lms 에서 돌고 있는 방식입니다.
>
> ### 기각한 대안과 사유 — A (API 키)
>
> A 가 나은 점이 하나 있습니다. **무인 서버 상시 실행**입니다. CLI 방식은 로그인 세션에 의존하므로, "교대 1시간 전 자동 생성"을 서버에서 무인으로 돌릴 때 불안정할 수 있습니다. 이것은 실제 약점입니다.
>
> 그런데 이 약점이 물리는 구간이 없습니다.
> - **본선 제출**은 시연·재현이 목적이라 사람이 실행합니다
> - **실배포**는 A.Biz 이지 API 가 아닙니다
>
> 즉 A 를 채택해도 그 장점을 쓸 구간이 없고, ①②③ 의 대가만 치릅니다. 그래서 기각합니다.
>
> ## 함께 못 박을 설계 조건 — LLM 은 반드시 선택이어야 한다
>
> **재현 가능성 10점** 때문입니다. 심사위원이 직접 돌려봐야 하는데, 심사위원 PC 에는 Claude Max 로그인도 API 키도 없습니다.
>
> 그래서 `compose()` 는 **LLM 이 없으면 지금의 문장 틀로 조용히 내려가야** 합니다. `engine/api.py` 가 없으면 임시 엔진으로 내려가는 것과 똑같은 구조입니다. 실행 첫 줄과 화면에 어느 쪽이 도는지 표시하는 것도 같이 맞춥니다.
>
> **LLM 을 필수로 만들면 심사위원 환경에서 프로토타입이 아예 안 돌아갑니다.** 이건 25점(기능적 완성도)과 10점(재현 가능성)을 동시에 잃는 경로라 절대 하지 않습니다.

> # 난관 1 — 12시간에 시나리오 20종을 다 넣으려다, 안 되는 이유를 수치로 증명했다
>
> **무엇이 예상과 달랐나.** 포함률을 "20종 중 몇 종"으로 재려면 데이터 안에 20종이 다 있어야 했다. 처음 생각은 단순했다 — 12시간 근무 하나에 20종을 중복 허용으로 던져 넣으면 되지 않나. 넣어보기 전에 합산부터 해봤는데, 20종의 지속시간 합이 **41.8시간, 12시간의 3.5배**였다. `TI-205` 하나는 혼자서 근무 창의 103%를 차지했다.
>
> **무엇을 시도했나 (순서대로).**
>
> 1. **몬테카를로 100회** — 랜덤 배치에서 같은 태그가 같은 시간에 겹치지 않는 경우가 있는지. 결과: **0/100.** 단 한 번도 깨끗하게 들어가지 않았다 (평균 충돌 3.9건).
> 2. **실제 데이터 20개 seed 생성** — 겹치면 실제로 뭐가 깨지는지. 결과: **설비정지 수준 알람(HH/LL) 침범이 20/20 seed 전부**에서 발생. "알람 미발생"으로 설계한 시나리오가 겹침 때문에 알람을 울리는 경우 5/20. 겹친 구간은 두 파형이 합성되어 **정답지에 적힌 것과 다른 제3의 파형**이 됐다 — 엔진이 뭘 잡아도 어느 시나리오인지 판정 불가.
> 3. **24시간 + 같은 태그 시간겹침 금지** — 20/20 배치 성공. 다만 하루 20건은 비현실적.
> 4. **팀 논의로 방향 전환** — "12시간에 6~10건 랜덤이면?" 재시뮬레이션: 충돌 0인 경우 57/100, 태그 단위 시간겹침만 피하면 **150/150.** 여기서 현장 관점이 하나 더 들어왔다 — **실제 현장에서는 이상이 동시에 나기도 하니, 겹침을 막지 말고 엔진이 그것도 잡는지 보자.**
> 5. **최종 설계** — 근무(12h) 단위 연속 생성, 동시 발생 허용, 설계가 무너지는 조합 두 개(`#2×#8`, `#1×#15`)만 회피. 채점용은 별도로 20종을 수동 배정한 2근무를 유지.
>
> **무엇을 남기고 무엇을 포기했나.** "한 파일에 20종 전수"를 포기했다. 대신 **채점용(수동 배정, `data/`)과 시뮬레이션용(랜덤, `data/sim/`)을 폴더로 분리**했다 — 섞이면 포함률 숫자의 근거가 무너진다.
>
> **새로 알게 된 것.** 이상이 데이터의 70%를 차지하면 검출기의 기준선이 **이상을 정상으로 학습**해 아무것도 못 잡는다. 채점용 시험지와 현실적인 하루는 다른 물건이고, 둘 다 필요하다. 그리고 감으로 싸울 뻔한 설계 논쟁이 몬테카를로 수치 앞에서 한 번에 끝났다.

> # 난관 2 — 현실성을 높이려 넣은 외기가, 내 모델의 모순과 엔진의 결함을 연달아 드러냈다
>
> **무엇이 예상과 달랐나.** 태그 53점이 각자 무작위로만 흔들려 데이터에 "하루"가 없었다. 현장 감각으로는 ASU 는 대기 온습도에 공정 전체가 끌려간다 — 그래서 대기 온도·습도에 24시간 일주기를 걸고 하류 22개 태그가 따라 움직이게 했다. 넣은 직후 검증은 전부 통과였다. **아침 한 시각에서만 돌렸기 때문이었다.**
>
> **무엇을 시도했나 (순서대로).**
>
> 1. 랜덤 검증 중 `#20`(전력 급증)이 **오후에 걸릴 때만** 설비정지 알람(HH)을 넘는 것을 발견. 시각을 옮겨 재검증하니 15시 주입에서 HH 를 26kW 초과.
> 2. 주입값을 440→380kW 로 낮춤 — 이번엔 **아침에 H 를 못 넘어** "알람 발생" 설계가 반대로 깨짐. 400kW — 07시에 여전히 실패. **주입값 조정으로는 못 푸는 구조**였다.
> 3. 원인 추적 — **내 외기 모델의 물리 모순**을 찾았다. 외기가 오르면 유량은 6.3% 내려가게 해놓고 전력은 올라가게 해뒀다. 실제로는 유량 감소(전력↓)와 IGV 보상(전력↑)이 상쇄되어 순 효과가 작다. 감도를 0.67→0.30 으로 고치자 12개 시각 전부 통과.
> 4. 검증 방법 자체를 교정 — **외기가 들어온 뒤로는 "언제 걸리느냐"가 결과를 바꾼다.** 이후 모든 시나리오 검증을 아침 한 시각이 아니라 12개 시각에서 돌린다.
> 5. 며칠 뒤 팀장의 독립 채점(`tools/score.py`)에서 후속 결함이 드러났다 — 엔진이 외기 일주기를 드리프트로 오인(오탐 근무당 10~11건, 17/20이 외기 기인), 그리고 핵심 시나리오 `#2` 미검출 (#13).
> 6. 두 결함이 같은 원인의 양면임을 정량화해 전달 — `TI-205` 의 외기 기인 정상 변동이 **15.4℃**, `#2` 신호는 12시간에 **8.2℃.** 정상 변동이 신호보다 2배 커서 어떤 문턱으로도 불가능하다. 해법 재료로 태그 마스터의 `amb_temp_gain`·`amb_humid_gain` 열과 생성기의 보상 공식을 엔진 담당에게 넘겼다.
>
> **무엇을 남기고 무엇을 포기했나.** 데이터는 그대로 남겼다 — 외기는 현실이고, 데이터가 아니라 엔진이 근무자처럼 외기를 감안해야 한다("여름 오후의 토출온도 115℃는 정상, 새벽의 115℃는 이상"). 포기한 것은 "한 시각 검증으로 충분하다"는 가정이다.
>
> **새로 알게 된 것.** 검출기 개발자가 만든 자체 픽스처에는 외기 연동이 없어서 **이 결함이 원리적으로 보일 수 없었다.** 데이터를 만든 사람과 검출기를 만든 사람이 달라야 하는 이유를 숫자로 확인했다 — 독립 측정이 아니었으면 제출물에 "포함률 100%(자체 측정)"라는 취약한 숫자를 들고 갔을 것이다.

> # 난관 3 — 현장 경험이 AI 의 작업을 네 번 뒤집었다
>
> 이 프로젝트는 도메인 담당(임도영)이 AI 로 데이터·화면을 만들고, 그 출력을 현장 경험으로 검증하는 방식으로 진행됐다. AI 가 만들고 현장이 뒤집은 순간들이 그대로 설계가 됐다.
>
> **① 알람 설계의 반전.** AI 는 "이상 시나리오는 알람에 안 걸려야 ENGRA 의 차별점"이라는 원칙으로 20종 전부를 알람 미발생으로 맞추려 했고, 연동 때문에 한계를 넘은 시나리오의 크기를 낮추자고 제안했다. 현장 판단은 반대였다 — **"알람이 울린 것 또한 ENGRA 가 확인하고 인수인계장에 넣어야 한다."** 알람이 울려도 적는 걸 잊으면 똑같이 누락이다. 이 한마디로 구조가 "미발생 13종 + 발생 7종"으로 바뀌었고, 발생 7종의 판정 기준은 "알람보다 먼저 잡는가"가 됐다 — 실측에서 엔진이 알람보다 최대 254분 먼저 잡는다는 숫자가 여기서 나왔다.
>
> **② 조치의 순서.** 시나리오별 조치 문구 초안에서 AI 는 GN2 공급압 저하의 첫 조치를 "수요처 통보"로 적었다. 현장 검토에서 빠졌다 — 실제 순서는 **LIN 액 밸브를 조정해 GN2 여유를 먼저 만들고, 공급밸브 개도를 올리고, 부족하면 B/U 를 추가 가동**한다. 대외 통보보다 설비 조작이 앞선다. 문헌에는 없는 현장의 순서다.
>
> **③ 물리가 파형의 모양을 정한다.** 순도 태그에 대칭 진동을 걸었더니 산소 순도 100.02% 가 생성됐다(팀장 발견, #7). 고치는 과정에서 현장 감각이 방향을 정했다 — **O2 순도는 위로 갈 여유가 0.4%p 뿐이라 실제 헌팅도 아래로만 크게 흔들린다.** 클램프로 자르는 게 아니라 하향 편향 진동으로 파형 자체를 다시 만들었고, 진동 함수에 물리 여유 검사를 넣어 재발을 막았다.
>
> **④ 기록의 문화.** 조치 문구를 다듬으며 현장이 고친 것 중 하나는 조치가 아니라 **문장**이었다 — "유량 제어 밸브 헌팅 확인, **현장 Leak 없음**, 제어 Gain 조정 검토 요청". 아니었던 사실도 적어야 다음 근무자가 같은 것을 다시 확인하지 않는다. "별도 조치 없이 추이 감시"도 빈칸이 아니라 판단의 기록이다. 이 원칙이 모의 과거 일지 시드 전체의 작성 기준이 됐다.
>
> **새로 알게 된 것.** AI 는 물리 문헌과 통계는 알지만 **현장의 순서**(조작이 통보보다 앞선다)와 **기록의 문화**(부정 소견도 적는다)는 모른다. 도메인 담당의 역할은 AI 를 시키는 것이 아니라 AI 의 출력을 검증하는 것이었고, 뒤집힌 판단들이 그대로 제품의 설계가 됐다.
