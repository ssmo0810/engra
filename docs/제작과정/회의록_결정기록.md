## #2 [요청] 검출 전처리 — 순간 스파이크가 기준선을 오염시키지 않도록

> ## 문제
> 12번 시나리오는 분석기 순간 스파이크입니다 — `MI-804` 값이 0.5 ppm에서 **999 ppm으로 3초간 폭등 후 원복**합니다 (정상값의 약 2,000배).

>

## #3 [결정] 시나리오별 현장 조치 사항 — 어디에 쓸 것인가
제기 ssmo0810 · 담당 dylim404 · 2026-08-15 · **처리 완료**

> 임도영님이 `docs/scenarios.md` 다음 작업에 올려주신 항목에 대한 정리입니다.
>
> ## 논점
> '각 시나리오의 현장 조치 사항'을 시나리오 문서에 적을 필요가 있는가?
>
> 실제 운영에서 조치 내용은 **근무자가 승인 화면에서 코멘트로 직접 입력**합니다. 미리 정해둘 성질이 아닙니다.
>
> ## 다만 한 가지 용도가 있습니다
> ENGRA에는 **과거 조치 추천** 기능이 있습니다 — 같은 태그·유사 증상의 과거 사례를 찾아 그때의 조치를 코멘트로 제안하는 것입니다. 데모 화면의 `과거 조치 추천 — 2026-06-12 야간조: 샘플링 의뢰 후 정상 확인` 이 그것입니다.
>
> 이 기능이 동작하려면 **과거 확정 일지에 조치 문구가 들어 있어야** 합니다. 즉 시연용 과거 일지를 만들 재료가 필요합니다.
>
> ## 제안
> - 시나리오 표에 조치 열을 넣되, 용도를 **'모의 과거 일지 시드'** 로 명확히 한다
> - 시나리오 1건당 조치 문구 1~2개면 충분 (실제 근무자가 쓸 법한 한 문장)
> - 우선순위는 낮음 — 20종 확장(#1)이 끝난 뒤
>
> ## 의견 주실 것
> - 이 용도로 필요하다고 보시는지
> - 아니면 과거 일지는 나중에 별도로 만들지

**논의와 결론**

- *dylim404* (2026-08-25) — **넣는 것으로 정했습니다.** 용도는 말씀하신 대로 **모의 과거 일지 시드** 하나입니다. 커밋 `9784b71`. ## 왜 필요한지 확인했습니다 ENGRA 의 과거 조치 추천(초안 파란 칸)은 **과거 확정 일지에 조치 문구가 있어야** 동작합니다. 그런데 시연 첫 화면에는 과거가 없어 빈칸이 됩니다. 파란 칸이 ENGRA 의 핵심 차별점인데, 그걸 보여주려면 근무를 2개 연달아 돌리고 1근무에서 사람이 코멘트를 타이핑해야 합니다. **5분 영상에서는 어렵습니다.** 미리 심어두면 첫 화면부터 채워집니다. 그것 하나를 위한 것이고, **실제 운영의 조치는 근무자가 승인 화면에서 직접 입력한다**는 판단은 그대로 유지했습니다. ## 넣은 위치 `docs/scenarios.md` 에 **별도 표**로 넣었

> ```

## #7 [요청] 데이터 생성기 — 순도 태그에 대칭 진동을 걸면 100% 를 넘습니다
제기 ssmo0810 · 담당 dylim404 · 2026-08-24 · **처리 완료**

> **누구에게** — 임도영 (`docs/`)
>
> **무엇이 필요한가**
>
> `osc()` 가 진폭을 대칭으로 더하는데 클램프가 없어서, 순도 태그에 물리적으로 불가능한 값이 생성됩니다.
>
> ```js
> function osc(D,tag,s,e,amp,period,decay){
>   D[tag][i] += amp*(...)*Math.sin(...)   // 상한 검사 없음
> }
> ```
>
> 시나리오 1은 `AI-707` 에 amp 0.42 를 겁니다. 기저값이 99.6 이므로 상향 진동에서 **99.6 + 0.42 = 100.02%** 가 나옵니다. 산소 순도가 100% 를 넘을 수는 없습니다.
>
> **왜 필요한가**
>
> 이 CSV 가 두 곳으로 갑니다.
>
> 1. 정기영님 검출 엔진 입력 — 불가능한 값이 기준선을 오염시킵니다 (#2 와 같은 종류의 문제)
> 2. **제출물 「03. 검증 환경」의 데이터 세트** — 심사위원이 열어봅니다. 순도 100.02% 가 있으면 데이터 신뢰도가 깎입니다
>
> **제안**
>
> `osc()` 에 태그 마스터의 `normal_lo`/`normal_hi` 로 클램프를 걸거나, 순도처럼 상한이 물리적으로 막힌 태그는 **하향 편향 진동**으로 처리하는 방법이 있습니다.
>
> 참고로 데모 차트에서 같은 문제를 만나 이렇게 처리했습니다 — 중심을 99.45 로 두어 최저 99.18(시나리오 값 그대로)·최고 99.72(정상 상한 99.9 안)로 맞췄습니다. 시나리오 표의 `±0.42%p` 표기도 **하향 0.42** 로 읽는 것이 맞아 보입니다(최저 99.18 과 일치).
>
> **확인 방법**
>
> 생성한 CSV 에서 `AI-707`·`AI-803` 최대값이 각 태그 `normal_hi` 를 넘는지 보시면 됩니다.
>
> **언제까지**
>

제기 ssmo0810 · 담당 ssmo0810 · 2026-08-25 · **처리 완료**

> ## 무엇을 정하는가
>
> `app/ports.py` 의 `compose()` 는 지금 문장 틀로 동작합니다. 여기에 LLM 을 붙이는 방법이 두 가지입니다.
>
> - **A. API 키 방식** — `anthropic` SDK 를 설치하고 API 키로 호출
> - **B. CLI 서브프로세스 방식** — `claude` / `codex` 실행 파일을 `subprocess` 로 호출, 구독 계정 사용
>
> ## 결론 — B (CLI 서브프로세스)
>
> ### 선례가 이미 있다
>
> `cs-study-lms` 가 같은 문제를 B 로 풀어 운영 중입니다 (`scripts/auto-evaluate.js`).
>
> ```
> codex exec --ephemeral --ignore-user-config --sandbox read-only
>            --output-schema evaluation-result.schema.json
>            --output-last-message result.json --cd <workDir>
> ```
>
> 프롬프트는 stdin, `spawnSync`, 타임아웃 10분, 버퍼 50MB. `EVALUATOR_PROVIDER` 환경변수로 `claude -p --tools Read` 경로와 갈아끼웁니다. **API 키가 코드 어디에도 없습니다.** 재시도 지연(`RETRY_DELAYS_MS`)과 잠금 파일까지 붙어 있어, 서브프로세스 LLM 호출에 필요한 것이 무엇인지도 이미 학습돼 있습니다.
>
> ### ENGRA 에 B 가 맞는 이유
>
> **① 기획서의 "외부 의존 0" 주장을 지킨다.** 기획서 4-3 에 "`app/`·`tools/` 의 모든 import 가 파이썬 표준 라이브러리, 의존성 선언 파일 없음"을 실측으로 적었습니다. `anthropic` SDK 를 넣으면 이 문장이 거짓이 되고, Ground Rule 의 **오픈소스 라이선스 준수·출처 명시** 의무도 새로 생깁니다. `subprocess` 는 표준 라이브러리입니다.
>

>
> **③ 실배포 이식 경로가 A.Biz 다.** 사내는 폐쇄망이라 최종적으로 A.Biz 어댑터로 가야 합니다. API SDK 를 박으면 나중에 **걷어내는** 작업이 추가됩니다. `compose()` 하나만 교체하는 구조면 CLI든 A.Biz든 같은 자리입니다.
>
> **④ 구조화 출력이 API 못지않다.** `--output-schema` 로 JSON 스키마를 강제할 수 있습니다. 추정이 아니라 cs-study-lms 에서 돌고 있는 방식입니다.
>
> ### 기각한 대안과 사유 — A (API 키)
>
> A 가 나은 점이 하나 있습니다. **무인 서버 상시 실행**입니다. CLI 방식은 로그인 세션에 의존하므로, "교대 1시간 전 자동 생성"을 서버에서 무인으로 돌릴 때 불안정할 수 있습니다. 이것은 실제 약점입니다.
>
> 그런데 이 약점이 물리는 구간이 없습니다.
> - **본선 제출**은 시연·재현이 목적이라 사람이 실행합니다
> - **실배포**는 A.Biz 이지 API 가 아닙니다
>
> 즉 A 를 채택해도 그 장점을 쓸 구간이 없고, ①②③ 의 대가만 치릅니다. 그래서 기각합니다.
>
> ## 함께 못 박을 설계 조건 — LLM 은 반드시 선택이어야 한다
>

>
> ```python
> class UrlSource:
>     """URL 의 CSV. 형식은 CsvSource 와 같다."""
>     def __init__(self, url):
>         self.url = url
>         self.name = f"url:{url.rsplit('/', 1)[-1]}"
>     def read(self):
>         with urllib.request.urlopen(self.url) as r:
>             text = io.TextIOWrapper(r, encoding="utf-8-sig", newline="")

> # 난관 3 — 현장 경험이 AI 의 작업을 네 번 뒤집었다
>
> 이 프로젝트는 도메인 담당(임도영)이 AI 로 데이터·화면을 만들고, 그 출력을 현장 경험으로 검증하는 방식으로 진행됐다. AI 가 만들고 현장이 뒤집은 순간들이 그대로 설계가 됐다.

> **새로 알게 된 것.** AI 는 물리 문헌과 통계는 알지만 **현장의 순서**(조작이 통보보다 앞선다)와 **기록의 문화**(부정 소견도 적는다)는 모른다. 도메인 담당의 역할은 AI 를 시키는 것이 아니라 AI 의 출력을 검증하는 것이었고, 뒤집힌 판단들이 그대로 제품의 설계가 됐다.

## #23 [소견] 검출이 신호 크기에 단조롭게 반응하지 않습니다 — 중간 크기 이상에 사각지대 가능성

> ## 무엇을 했나
>
> 우리 시나리오는 전부 노이즈보다 한참 큽니다. 그래서 「100% 검출」이 당연한 것 아닌가 싶어,

> 대상은 `#9` Cold end 저온 이탈 (`TI-403`).
>
> 방법은 깨끗한 데이터와 주입한 데이터를 각각 만들어 그 차이만 배율로 섞었습니다.
> 파형 모양은 그대로 두고 크기만 정확히 줄이는 방식입니다.
>
> ```
> D_scaled = clean + (injected − clean) × factor
> ```
>
> ## 결과
>
> | 배율 | 신호/노이즈 | TI-403 | 판정 |
> | ---: | ---: | --- | --- |
> | 1 | 90.0 | 드리프트 | 검출 |
> | 0.3 | 27.0 | — | **놓침** |
> | 0.15 | 13.5 | — | **놓침** |
> | 0.08 | 7.2 | 드리프트 | 검출 |
> | 0.04 | 3.6 | — | 놓침 |
> | 0.02 | 1.8 | — | 문턱 아래 — 정상 |
>
> **0.3 배를 놓치는데 0.08 배를 잡습니다.** 크기를 줄일수록 못 잡아야 정상인데 그렇지 않습니다.
>

>
> 처음엔 6근무를 한 DB 에 순서대로 넣어서 앞 근무의 이상이 뒤 근무 기준선을 오염시킨 줄 알았습니다.

> **결과가 같았습니다.**
>
> ## 제 지표가 엔진 k 가 아닙니다 (정정)
>
> 위 표의 「신호/노이즈」는 제가 만든 어림값입니다. 엔진 지표를 직접 열어보니

> - **최하단 상시 노출** — 아예 숨기지 않으니 **묻히지 않습니다.** 접혀 있어 읽기 부담도 없습니다
> - **조건부 승격** — 「전에 제외했으니 계속 제외」 를 막습니다. **상황이 나빠지면 다시 올라옵니다**
> - **72시간 만료** — 오래된 판단이 영원히 따라다니지 않게 합니다
>
> > **오늘 QA 의 「선의로 쓴 틀린 코멘트」 시험과 같은 계열의 문제입니다.**
> > 앞 근무자가 좋은 뜻으로 「무시해도 됨」 을 남기면 그 판단이 계속 따라다닙니다.
> > 숨김 처리도 똑같아서 — **한 번의 제외가 영구 삭제가 되면 안 됩니다.**
>
