# 서비스 구현

수집부 · 저장소 · 승인 처리 · 화면. 세 사람의 산출물이 실제로 돌아가게 연결되는 곳입니다.

- 담당: 박경모
- 본선 기간에 이 폴더에서 프로토타입을 만듭니다. **제출 마감 2026-09-03(목) 23:59.**

---

## 구성

| 영역 | 하는 일 |
| --- | --- |
| 수집부 | 지정 시각에 근무 구간 데이터를 조회해 적재. 실배포 시 데이터 소스만 교체 가능하도록 분리 |
| 저장소 | 원본 시계열(단기 회전) · 근무별 요약 · 베이스라인 · 이벤트 · 초안 · 확정 일지 |
| 승인 처리 | 채택·제외를 항목 단위로 기록 → 확정 일지 생성 → 색인 갱신 → 베이스라인 제외 구간 반영 |
| 화면 | 초안 검토(전 항목 표시·선택·코멘트·승인), 일지 조회 |
| 스케줄러 | 구간이 닫히는 시각에 수집 → 검출 → 초안 생성을 자동 실행 |

---

## 실행

**설치할 것이 없습니다.** 파이썬 3.10 이상이면 바로 돕니다. 외부 라이브러리를 쓰지 않은 것은
세 사람이 각자 다른 환경에서 설치 없이 돌릴 수 있어야 하기 때문입니다.

```bash
bash tools/smoke.sh                      # 배선 전 구간 한 번에 확인 (권장)

python3 app/cli.py init                              # 저장소 생성
python3 app/cli.py sample --date 2026-08-22          # 배선 확인용 소형 CSV
python3 app/cli.py ingest app/sample_shift.csv
python3 app/cli.py run 2026-08-22-day                # 요약 → 기준선 → 검출 → 초안
python3 app/cli.py draft 2026-08-22-day              # 초안 보기
python3 app/cli.py serve                             # 웹 화면 http://127.0.0.1:8000
```

**근무 ID 는 날짜에서 나옵니다**(`YYYY-MM-DD-day`). `--date` 를 안 주면 오늘 날짜로 만들어지므로,
`sample` 과 `ingest` 가 다음에 칠 명령을 출력해 줍니다.

임도영님 생성기가 만든 시나리오 CSV 도 `ingest` 에 그대로 넣으면 됩니다.
`sample` 은 배선 확인용이라 태그가 5개뿐입니다 — 성능 측정에 쓰지 마세요.

## 코드 구조

| 파일 | 하는 일 |
| --- | --- |
| `config.py` | 경로와 근무 구간 규칙 |
| `db.py` | 저장소 6종 (원본·요약·기준선·이벤트·초안·확정일지 + 색인) |
| `collect.py` | 데이터 소스와 적재. 실배포 시 `CsvSource` → `RtdbSource` 만 교체 |
| **`ports.py`** | **엔진 자리.** 아래 참고 |
| `stub_engine.py` | 임시 엔진. 엔진이 오면 자동으로 물러난다 |
| `pipeline.py` | 한 근무를 처음부터 끝까지 |
| `approve.py` | 승인 → 확정 일지 → 색인 |
| `server.py` | 웹 화면 (표준 라이브러리) |
| `cli.py` | 명령줄 |

### 엔진 자리 (`ports.py`)

검출과 초안 작성은 `app/` 이 직접 하지 않고 **포트를 거칩니다.**
`engine/api.py` 에 아래 네 함수가 생기면 `ports.py` 가 자동으로 그쪽을 쓰고,
**`app/` 코드는 한 줄도 고치지 않습니다.**

```python
summarize(series)                       -> {태그: 요약}
build_baseline(summaries)               -> {태그: 기준선}
detect(series, baselines)               -> [이벤트, ...]
compose(shift, events, find_precedents) -> [초안항목, ...]
```

지금 무엇이 돌고 있는지는 화면 오른쪽 위와 `cli.py init` 출력에 `stub` / `engine` 으로 표시됩니다.
**형식이 규약과 다르면 조용히 넘어가지 않고 그 자리에서 멈춥니다** — 통합이 깨지는 가장 흔한
원인이 "형식이 조금 달랐는데 아무도 몰랐다" 이기 때문입니다.

구현 예시는 `stub_engine.py` 를 보면 됩니다. 그대로 복사해 `engine/api.py` 로 옮기고
내용만 채우면 붙습니다.

> 임시 엔진은 **알람 한계선(LL/L/H/HH)을 넘었는지만** 봅니다. 헌팅·드리프트·상관 붕괴처럼
> 알람에 안 걸리는 신호는 전혀 못 잡습니다. 시나리오 20종 중 알람이 울리는 건 2종뿐이라
> 임시 엔진의 성적은 2/20 근처에서 멈추고, 나머지 18종이 `engine/` 이 존재하는 이유입니다.

## 연결 규약 — 통합을 위해 먼저 합의할 것

세 사람이 각자 만든 것을 나중에 붙이면 서로 맞지 않아 다시 짜게 됩니다.
**아래 세 가지 형식만 미리 고정하면, 통합은 코드를 고치는 일이 아니라 연결하는 일이 됩니다.**
본선 시작 전에 셋이 함께 확정합니다. 아래는 논의 출발점입니다.

### ① 모의 데이터 → 시스템 (임도영 산출물)

근무 구간 시계열. CSV 한 장.

```
timestamp,tag,value
2026-08-02T06:00:00,AI-1201,99.20
2026-08-02T06:00:02,AI-1201,99.21
```

- 2초 주기, 태그 53점(`docs/tag_master.csv` 기준), 12시간 구간
- 시나리오 주입 위치와 종류는 별도 파일로 함께 제출 (검출 성능 채점의 정답지)

### ② 검출기 → 시스템 (정기영 산출물)

이벤트 목록. 함수 하나로 노출합니다.

```
detect(구간_시계열, 베이스라인) -> 이벤트 목록
```

이벤트 한 건에 담길 것:

| 항목 | 설명 |
| --- | --- |
| 태그 | 어느 태그에서 발생했나 |
| 시작·종료 | 구간의 시각 |
| 유형 | 헌팅 / 드리프트 / 레벨시프트 / 임계근접 / 이탈 |
| 지표 | 판정 근거 수치 (예: 베이스라인 대비 4.2배) |
| 중요도 | 상 / 중 / 하 또는 점수 |
| 근거 문장 | 사람이 읽을 수 있는 한 줄 |

### ③ 시스템 → 화면

초안 항목. 이벤트에 과거 사례와 코멘트 추천을 붙인 형태이며, 채택 여부(`adopted`)를 **항목 단위**로 기록합니다.
제외한 항목도 함께 저장합니다 — 감도 조정과 근무자 간 기준 차이 측정의 유일한 데이터입니다.

## 통합은 언제 하나

매주 말에 한 번씩 합칩니다. 몰아서 하지 않습니다.

| 시점 | 붙이는 것 | 확인 |
| --- | --- | --- |
| 1주 차 말 | 모의 데이터 + 검출기 | 데이터를 넣으면 이벤트 목록이 나온다 |
| 2주 차 말 | 초안 생성 + 승인 화면 | 데이터 투입부터 일지 확정까지 이어진다 |
| 3주 차 | 안정화 | 반복 시연에서 실패하지 않는다 |

각자 자기 폴더에서 작업하되, 위 규약대로 만들면 통합 시 고칠 것이 거의 없습니다.
규약을 바꿔야 할 일이 생기면 **바꾸기 전에 팀에 알립니다.** 말없이 형식을 바꾸는 것이 통합을 깨뜨리는 가장 흔한 원인입니다.
