# ENGRA 처리 시간 — 단계별·규모별 실측

2026-09-14 · 브랜치 `probe/probe-speed` · AI 호출 없음(`ENGRA_LLM=off`) · 저장소 코드(`app/`·`engine/`)는 고치지 않고 함수만 불렀다.
기계: MacBook Pro M5 Pro(CPU 15코어 = 성능 5 + 효율 10) · 메모리 48GB · Python 3.14.6 · SQLite 기본 설정(page 4096 · cache 2MB).
측정 중 load average 2~4 — 같은 기계에서 다른 세션이 함께 돌았다. 규모마다 2회 잰 합계의 차이는 6% 이내다.
커밋에는 이 문서와 결과 파일(`*.jsonl`·`*.log`·`table.txt`·`profile_*.txt`)만 넣었다 — 측정 스크립트(`*.py`·`*.sh`)는 워크트리 `tmp_speed/` 에만 있다(팀장 지시).
이 문서의 수치를 원자료와 codex 로 대조해 나온 5건(§12)은 고쳤지만, 고친 문서를 다시 대조하지는 않았다.

## 한눈에

- **지배 단계는 적재와 로드다.** 1,060태그 257초 중 적재(CSV→DB) 141초 55% · 로드(DB→메모리) 63초 24% · 묶음 28초 11% · 뷰 11초 · 요약 10초 · run_all 3.4초. 530태그는 적재 63% · 로드 22%.
- **곡선.** 요약·뷰·run_all 은 선형(b≈1.0), 적재 b 1.1~1.4, 로드 b 1.4~2.1, **묶음(`api._group`)은 모든 규모에서 b≈3.0**. 합계는 530→1,060 에서 b=1.28.
- **메모리 = 188 B/점 + 43MB** (5규모 잔차 ±1MB). 530태그 최고치의 88%가 로드 한 단계에서 생긴다 — `(시각 문자열, 실수)` 튜플이 점마다 따로 만들어진다(§4).
- **태그 분할 병렬은 순차와 바이트 단위로 같다 — 조건 둘.** ① links 연결 성분을 쪼개지 않고 외기 태그 둘(TI-101·MI-102)을 모든 워커에 넣는다. ② 부모가 합칠 때 순차 `run_all` 순서로 되돌린 뒤 묶는다. ②를 빼면 이벤트와 묶음 구성은 같고 **묶음 번호만** 달라진다. 530태그 N=8 이 5.4초(파이프라인 그대로 순차 31.4초) — 그중 3.6초가 부모의 묶음 단계.
- **분할 규칙을 깨면 결과가 바뀐다.** 외기 태그를 빼면 드리프트가 +96건(530태그, 09-11 주간). 상관이탈이 10건인 근무(09-10 주간)를 무작위로 나누면 끊긴 쌍 위 상관이탈 6건이 사라지고 나머지는 그대로다 — 같은 근무를 연결 성분으로 나누면 통째 같다.
- **적재는 고유 시각마다 한 번 변환 + `csv.reader` 로 66.9초 → 48.3초(1.38배), 결과 DB 3,434만 행 동일.** 파이썬 쪽은 −73% 지만 SQLite `executemany` 42초가 남아 다음 병목이다.
- **묶음이 3제곱인 원인은 `api._neighbours` 가 부를 때마다 태그 마스터 전체를 훑는 것이다.** 이 프로세스 안에서만 미리 계산한 사전으로 바꿔 끼우면 1,060태그 29.18초 → 0.038초, 결과는 통째로 같다.
- **외삽.** 1,000태그 ≈ 238초 · 3.9GB(실측 사이 보간). 1억 점(4,630태그, 12시간·2초 유지) ≈ 3,708초 · 18GB — 그중 묶음이 2,387초. 묶음만 사전으로 바꾸면 ≈ 1,322초. 18GB 가 병목인지는 운영 서버 메모리 한도(미확인)에 달렸다.

## 1. 방법

- **데이터** — `scale.py`. 53태그 근무 CSV 3개(12시간 × 2초 = 태그당 21,600점)를 K배 복제한다. 복제 태그는 `TAG_2`… 접미사,
  값은 30% 확률로 기록 자릿수 ±1눈금 잡음. `links` 도 같은 접미사로 옮겨 **사본 안에서 연결 구조를 유지**한다.
  외기 태그(`core.NOISE_TAGS` = `TI-101`·`MI-102`)는 이름 두 개로 고정이라, 사본(`TI-101_2`…)은 외기 기준자가 아니다 — 모든 태그가 원본 두 태그에 기댄다.
- **단계 시간** — `bench.py`. `prep` = 지난 근무 2개(09-10 주·야) 적재 + `pipeline.run` → base DB.
  `run` = base 복사 → 대상 근무(2026-09-11-day) 적재부터 초안 저장까지 `app/pipeline.run` 순서대로 쪼개 `perf_counter`.
  규모마다 2회 + cProfile 1회(`profile_x*_*.txt`), 교차 확인으로 같은 프로세스에서 `pipeline.run` 통째 1회. `--mem` 은 단계마다 RSS 를 남긴다.
- **단계 이름과 실제로 잰 범위** — 이름은 대표 함수이고, 타이머에는 그 앞뒤 DB 읽기가 함께 들어 있다(`bench.py` `stages()`).
  적재 = `collect.ingest`(CSV→`raw_sample`) · 로드 = `db.load_series`(DB→`{태그: [(ts, 값)]}`) · 요약 = `summarize` ·
  기준선 = `db.load_summaries` + `db.quality_bad_pairs` + `build_baseline` · 뷰 = `db.load_baselines` + `core.build_views` · run_all = `detectors.run_all` ·
  묶음 = `api._group` + 정렬 · 파형·초안 = `pipeline._waveform` + `db.load_events`·근무 조회·`compose`(과거 사례 검색 포함)·`quality_items` · DB쓰기 = `save_*`.
- ⚠ 중간 보고의 「530태그 적재 22~24초」 는 **적재(CSV→DB, 66~69초)가 아니라 로드(DB→메모리)** 였다 — `par.log` 의 `load_series` 값이다.

## 3. 곡선 — 로그-로그 기울기 b (시간 ∝ 태그 수^b)

| 단계 | x1→x2 | x2→x5 | x5→x10 | x10→x20 | 최소제곱 x5~x20 |
|---|---:|---:|---:|---:|---:|
| 적재 | 1.10 | 1.42 | 1.37 | 1.08 | 1.22 |
| 로드 | 1.03 | 1.04 | 2.08 | 1.43 | 1.76 |
| 요약 | 1.03 | 1.06 | 0.95 | 0.97 | 0.96 |
| 기준선 | 0.98 | 1.07 | 0.93 | 1.05 | 0.99 |
| 뷰 | 1.02 | 1.03 | 1.01 | 1.04 | 1.02 |
| run_all | 1.02 | 1.01 | 0.99 | 0.99 | 0.99 |
| 묶음 | 3.15 | 3.10 | 3.02 | 3.01 | 3.02 |
| 파형·초안 | 1.02 | 1.28 | 1.04 | 0.64 | 0.84 |
| DB쓰기 | 0.91 | 1.33 | 0.35 | 0.75 | 0.55 |
| 합계 | 1.07 | 1.30 | 1.48 | 1.28 | 1.38 |
| 적재 제외 | 1.03 | 1.08 | 1.68 | 1.56 | 1.62 |

- 요약·기준선·뷰·run_all 은 태그마다 한 번 도는 루프라 선형이다. 파형·초안·DB쓰기는 1초 미만이라 기울기가 흔들린다.
- **로드**는 265→530 에서 b 2.08 로 튄다. run_x10.db 에 `EXPLAIN QUERY PLAN` 을 한 번 돌린 출력(로그 파일로 남기지 않았다)은
  `db.load_series` 쿼리가 `SEARCH raw_sample USING INDEX idx_raw_ts (ts>? AND ts<?)` + `USE TEMP B-TREE FOR ORDER BY`,
  태그 IN 목록 쿼리가 `SEARCH raw_sample USING PRIMARY KEY (tag=? AND ts>? AND ts<?)` 였다. ts 색인으로 행을 찾고 값을 PK 에서 다시 읽은 뒤
  임시 정렬하는 것으로 본다(계획으로 본 해석). 같은 530태그를 태그 IN 목록으로 읽으면 22.0초 → 4.0초이고, GC 를 꺼도 21.3초라 GC 탓이 아니다(§6).
- **묶음**은 `_group` 이 이벤트 쌍(E²)마다 `_linked` → `_neighbours` 를 두 번 부르고, `_neighbours` 가 부를 때마다 태그 마스터 전체(T)를 훑는다.
  E 가 T 에 비례하니 T³ 이다 — §8 의 사전 대체 실험으로 확인했다.

최대 메모리 = **188 B/점 + 43MB** (5규모 직선 최소제곱, 잔차 ±1MB).

530태그 단계별 (`bench.py run --scale 10 --mem` → `mem.jsonl`):

|---|---:|---:|
| 시작 | 31MB | 31MB |
| 적재 | 37MB | 37MB |
| **로드** | **1,887MB** | 1,887MB |
| 요약 · DB쓰기 · 기준선 · DB쓰기 | 1,890MB | 1,890MB |
| 뷰 | 2,090MB | 2,090MB |
| run_all · 묶음 | 2,090MB | 2,090MB |

- 적재는 5,000행씩 흘려 넣어 6MB 만 더 쓴다. **로드가 +1,850MB(최고치의 88%)**, 뷰가 +200MB. 로드 +1,850MB ÷ 1,144.8만 점 ≈ 169 B/점.
- 그 크기의 내역: `sys.getsizeof` 로 한 점을 찍어 보면 튜플 64B + 시각 문자열 60B + 실수 24B + 리스트 칸 8B = 156B 이고, SQLite 에서 같은 시각을
  두 번 읽으면 다른 문자열 객체였다(`is` → False). 둘 다 Python 3.14 에서 한 번 돌린 명령 출력이라 로그 파일은 없다. 나머지는 리스트 여유분으로 본다.
- 단계가 끝나도 RSS 가 내려가지 않는다 — 파이프라인이 `series` 를 파형 단계(`pipeline._waveform`)까지 쥐고 있다.
- `docs/scenarios.md` 의 「848태그 × 21,600점 × 8바이트 ≈ 146MB」 는 계산 추정이었다. 이 직선으로 848태그는 약 3.3GB(보간) — 약 23배.
  같은 절의 「서버 MemoryMax 700MB」 는 저장소 `deploy/` 유닛 파일에 없다(`grep -rni memory deploy` 0건, 서버 실제 설정은 미확인).
  700MB 가 맞다면 이 직선으로 **약 170태그**에서 넘는다(보간).

## 5. 태그 간 의존 — 어느 함수가 다른 태그 값을 읽나

| 함수 | 다른 태그를 읽나 | 무엇을 |
|---|---|---|
| `api.summarize` · `api.build_baseline` | 아니오 | 태그별 루프 |
| `core.build_views` → `core._apply_noise_model` → `TagView.fit_noise` | **예** | `NOISE_TAGS`(TI-101·MI-102) 뷰를 기준자로 **모든 태그**의 `adj`·`s_adj`·`amb` 를 만든다. 이 셋은 `detectors.drift` 만 쓴다 |
| `core._independent` | 예 (외기 태그끼리) | 기준자끼리 겹치는 몫 제거 |
| `detectors.run_all` 의 단일 검출기 7종 (`limit_crossings`·`drift`·`level_shift`·`hunting`·`spike`·`near_limit`·`stuck`) | 아니오 | 뷰 하나씩 |
| `detectors.residual` (`run_all` 연결 쌍 루프) | **예** | 태그 마스터 `links` 의 상대 태그 뷰 |
| `api._group` → `_linked` → `_neighbours` | **예 (이벤트 전체)** | 시간 겹침 + links 직접 연결·공유 이웃 + `metrics.pair`. 묶음 번호는 `max(score)` 정렬이라 **동점이면 입력 순서가 번호를 정한다** |
| `api.detect` 마지막 정렬 | 순서 | (중요도, −점수, 시작) 동점이면 입력 순서 |
| `api.compose` · `ports._stop_question` | 예 (이벤트 전체) | 묶음 번호별 항목 · 10분 창 동시 이탈 태그 수 — 검출 **뒤** 단계 |
| `core.epoch` 의 `_TS_CACHE` | 전역 캐시 | 순수 함수 값 캐시 — 결과에 영향 없음 |

## 6. 태그 분할 병렬 — 결과가 순차와 같은가 (530태그)

### 1차 (`par.py` · `par.log`, 이전 워커)

links 연결 성분(530태그에서 270개, 최대 9태그)을 쪼개지 않고 가장 가벼운 묶음에 넣고, `NOISE_TAGS` 두 태그를 모든 워커에 보조로 넣었다.
워커는 담당 태그 이벤트만 돌려주고 부모가 합쳐 `_group`·정렬을 한 번 돈다. 이벤트 330건은 N 전부 같았지만
판정은 「순차와 동일=False (묶음 번호·관련 태그 빼면 True)」 였다. 순진한 분할(태그 이름순 등분, 보조 없음) N=4 는 390건 · 순차와 차집합 100건.

### 2차 (`par2.py parallel --scale 10` → `par2_parallel_x10.log`)

**로드 방식** — 같은 프로세스, 530태그 1,144.8만 점. B·C 는 결과 dict 가 A 와 같다(A2 는 시간만 쟀다). 쿼리 계획은 §3.

| 방식 | 초 |
|---|---:|
| A `db.load_series` (ts 색인 + ORDER BY 임시 정렬) | 21.98 |
| B 같은 것 + GC 끔 | 21.30 |
| C 태그 IN 목록 (PK 탐색) | **4.02** |
| A2 A 다시 | 20.87 |

**순차 vs 병렬** — links 연결 성분 분할 + 외기 태그 보조. 초는 회차별.

| 순차 (IN 목록 로드) | — | — | 14.48 | — | 통째 같음 True | — |

- 「이어 붙이기만」 의 통째 False 는 **묶음 번호뿐**이다 — 어느 이벤트끼리 묶였는지는 N 전부 같다. `_group` 이 번호를 `max(score)` 로만 정렬해
  동점을 입력 순서로 두는데, 복제 데이터는 사본 태그끼리 점수가 같아 동점이 흔하다(실데이터도 동점이 날 수 있다).
- **부모가 `(단일/연결 쌍, 기준 태그 순서, 워커 안 순번)` 으로 되돌린 뒤 묶으면 번호·순서까지 통째 같다** — N=2·4·8·15, 7회 전부.
  같은 (단계, 기준 태그) 이벤트는 한 워커에서만 나오므로 워커 안 순번이 곧 순차 순번이다. 전제(뷰 순서 = 태그 정렬, 연결 쌍 이벤트가 전부 뒤)는 스크립트가 실제 데이터로 assert 한다.
- 속도: 워커는 N=2 5.9초 → N=4 3.0초 → N=8 1.82초로 8까지는 거의 N 에 비례해 줄고, N=15 는 1.30초로 둔화한다(성능 코어 5개).
  부모의 묶음 3.56초는 N 과 무관해 N=8 합계의 66%다. 기준을 같은 로드(IN 목록) 순차 14.48초로 잡으면 N=8 은 2.7배, 파이프라인 그대로(31.4초)면 5.8배.
- 묶음을 사전 대체(§8, 530태그 0.009초)로 바꾸면 N=8 은 워커 1.82초 + 묶음 약 0.01초가 된다 — 따로 잰 두 값의 합일 뿐, 한 번에 돌려 잰 값은 아니다.

**분할 규칙을 하나씩 깨면** — N=4, 대상 근무 2026-09-11-day, 순서 복원 후 비교.

## 7. 적재 개선 실험 — 고유 시각마다 한 번 변환 (530태그)

`ingest_fast.py bench --scale 10` → `ingest_fast_x10.log`. 변형마다 새 프로세스 · base DB 복사본 · 실행 직전 CSV 예열 · 3회 자리 돌림(각 변형이 첫째·둘째·셋째 자리에 한 번씩).

| 변형 | 적재 3회 (초) | 평균 | orig 대비 | 그중 `executemany` | 나머지 (파이썬 행 처리·커밋) | 최대 메모리 |
|---|---|---:|---:|---:|---:|---:|
| orig — `collect.ingest` 그대로 | 69.49 · 64.79 · 66.31 | 66.9 | 1.00배 | 44.4 | 22.5 | 35MB |
| cache — 시각 원문 → (저장용 ISO, 근무 판정) 사전 | 55.86 · 52.40 · 55.22 | 54.5 | 1.23배 | 44.9 | 9.6 | 44MB |
| reader — cache + `csv.reader` | 47.73 · 47.83 · 49.41 | 48.3 | **1.38배** | 42.3 | **6.1** | 44MB |

- **결과 DB 가 같다** — cache·reader 모두 orig 와 `raw_sample` 전 34,344,000행(지난 근무 2개 + 대상), `shift` 행(적재 시각 제외), 근무별 행 수가 같다.
- 한 근무 파일의 서로 다른 시각은 21,600개뿐이라 1,145만 번 하던 `fromisoformat`·`shift_id_for`·`isoformat` 이 21,600번으로 준다.
  사전은 행 수가 아니라 고유 시각 수만큼만 커서 파일을 메모리에 올리지 않는다(최대 메모리 35→44MB).
- 파이썬 쪽은 22.5초 → 6.1초(−73%)로 줄지만 **`executemany` 42~45초가 그대로 남아** 적재 전체는 1.38배에서 멈춘다.
  다음 병목은 SQLite 삽입이다 — `raw_sample` 은 `PRIMARY KEY (tag, ts)` WITHOUT ROWID 표와 `idx_raw_ts` 색인 두 곳에 쓴다(삽입 쪽 원인은 미측정).
- orig 평균 66.9초는 `results.jsonl` 의 530태그 적재 평균 66.92초와 맞는다 — 실험 틀이 규모 표 측정과 같은 조건이다.

## 8. 묶음 단계가 3제곱인 이유 (`par2.py group` → `group.jsonl`, 규모마다 1회)

| 태그 | 이벤트 | 묶음 수 | 원본 묶음·정렬 | `_neighbours` 사전 대체 | 사전 만들기 | 결과 통째 같음 | 연결 성분을 넘는 묶음 |
|---:|---:|---:|---:|---:|---:|:---:|---:|
| 265 | 163 | 31 | 0.428s | 0.002s | 0.008s | True | 0 |
| 530 | 330 | 61 | 3.501s | 0.009s | 0.036s | True | 0 |
| 1060 | 657 | 120 | 29.176s | 0.038s | 0.138s | True | 0 |

- 기울기(530→1,060): 원본 3.06 · 사전 대체 2.08 — 남는 것은 이벤트 쌍 루프(E²)다. ms 단위 1회 측정이라 2.08 은 참고치.
- **묶음은 links 연결 성분을 넘지 않는다**(3규모 0건). `_linked` 는 직접 연결·공유 이웃만 보고 `metrics.pair` 도 연결 쌍이라 코드로도 성분 안에서만 묶인다.
  그래서 묶음 계산 자체를 워커로 내리고 부모는 번호만 매기는 설계가 가능하다 — 선택지일 뿐 이번에 잰 것은 아니다.
- 원본 묶음 곡선이 다른 단계 곡선을 넘는 태그 수(530→1,060 기울기끼리, 외삽): run_all 은 530태그에서 이미 · 요약 약 640 · 뷰 약 660 ·
  로드 약 1,770 · 적재 약 2,450 · **나머지 단계 전부의 합 약 3,340태그**.

## 9. 외삽 — 실측 곡선만 근거로 늘린 값 (실측 아님)

530→1,060태그 사이 단계별 기울기 b 로 1,060태그 실측값을 늘렸다. 1,000태그는 실측 사이 **보간**, 4,630태그는 **외삽**이다.
「1억 점」 은 12시간·2초 간격을 유지한 채 태그를 늘린 경우(4,630태그 × 21,600점)로 읽었다.

| 단계 | 1,060 실측 | b | 1,000태그 (보간) | 4,630태그 = 1억 점 (외삽) |
|---|---:|---:|---:|---:|
| 적재 | 141.44 | 1.08 | 132.8 | 695 |
| 로드 | 62.72 | 1.43 | 57.7 | 517 |
| 요약 | 9.96 | 0.97 | 9.4 | 41.7 |
| 뷰 | 10.80 | 1.04 | 10.2 | 49.8 |
| run_all | 3.43 | 0.99 | 3.2 | 14.8 |
| 묶음 | 28.09 | 3.01 | 23.6 | **2,387** |
| 기타 (기준선·파형·초안·DB쓰기) | 0.96 | — | 0.9 | 2.5 |
| **합계** | 257.4 | | **238초** | **3,708초 (62분)** |
| 묶음만 사전 대체 (b 2.08) | | | 214초 | 1,322초 (22분) |
| **최대 메모리** (188 B/점 + 43MB) | 4,150MB | 직선 | **3.9GB** | **18.0GB** |

- 1,000태그는 지금 구조로 4분 · 4GB 안이다. 1억 점에서는 시간 62분 중 묶음 단계가 64%를 차지하고, 메모리 18GB 는 측정 기계(48GB)에는 들어간다.
  메모리가 병목이 되는지는 운영 서버 한도에 달렸다 — `docs/scenarios.md` 가 적은 700MB 가 맞다면 약 170태그에서 넘지만 그 한도는 미확인이다(§4).
- 태그를 그대로 두고 점만 늘리는 경우(더 긴 구간·더 짧은 간격)는 이벤트 수가 어떻게 변할지 몰라 이 곡선으로 말할 수 없다 — 미측정.

## 11. 함정

1. **적재 ≠ 로드.** 중간 보고의 「530태그 적재 22~24초」 는 로드(DB→메모리)였다. 적재(CSV→DB)는 66~69초.
2. **cProfile 은 파이썬 쪽을 부풀린다** — 530태그 적재 67→91초, 묶음 3.5→8.6초. 단계 비율은 프로파일을 끈 2회로만 냈다.
3. **`bench.py` 는 엔진 함수를 직접 부른다** — `ports.validate_events`·확정 일지 검사를 건너뛴다(`codex_bench.txt`). `pipeline.run` 통째 교차 확인이 10% 안이라 영향은 작다.
4. **복제 데이터는 점수 동점이 흔하다** → 이어 붙이기 병합은 묶음 번호가 달라진다. 실데이터도 동점이 날 수 있으니 병합 순서 복원을 규칙으로 둬야 한다.
5. **음성 대조 없이 「같다」 를 믿지 않았다.** 대상 근무(09-11 주간)는 상관이탈 0건이라 무작위 분할의 「같다」 가 links 무관의 근거가 못 됐다 → §6 양성 대조.
6. **`NOISE_TAGS` 는 이름 두 개 고정** — 사본(`TI-101_2`…)은 외기 기준자가 아니다. 어떤 분할이든 워커마다 원본 두 태그를 넣어야 한다.
7. **로드는 페이지 캐시 상태에 민감하다** — 한동안 안 읽은 265태그 DB 를 처음 읽을 때 13.5초(`group.jsonl`), 복사 직후 5.5초(`results.jsonl`).
8. **적재 실험의 순서 효과** — 처음엔 변형을 늘 같은 순서로 돌렸다(codex 지적 2차례) → 3회 자리 돌림 + 실행마다 CSV 예열로 고친 뒤 쟀다.
9. **`RAW_RETENTION_DAYS` 회전** — 지난 근무(09-10)와 대상(09-11)이 3일 안이라 `rotate_raw` 에 안 지워진다. 더 오래된 날짜를 쌓으면 지워진다.
10. **디스크** — `tmp_speed/db` 20GB+, `tmp_speed/data` 4.2GB. `.gitignore` 로 커밋하지 않는다.

## 13. 재현

측정 스크립트는 커밋하지 않았다 — 워크트리 `tmp_speed/` 에 있다.

```bash
python3 tmp_speed/scale.py 2 5 10 20              # 합성 CSV·태그 마스터 (data/, 4.2GB)
bash tmp_speed/run_all.sh                         # 규모 5개 × prep·run 2회·profile → results.jsonl (약 45분)

```

`data/`(CSV)·`db/`(SQLite)는 `.gitignore` — 위 명령으로 다시 만든다. 한 번에 하나씩 돌려야 서로 시간을 뺏지 않는다.
