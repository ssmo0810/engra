## 권고

- **틱 간격 5분.** 100배속 3초 간격에 틱 최대 0.92초(여유 3배). 10분 틱보다 알람 전 초안이 14 → 17건(R1), 가시화 지연 중앙 9 → 5분. 1분 틱은 10시간을 넘기면 밀린다.
- **등재 규칙 R2+** (한계선 교차는 즉시, 나머지는 연속 2틱). R3 는 알람 전 초안을 5분 틱 17 → 8건으로 잃는데 잘못 등재는 여전히 1,031건이다. R2+ 가 R2 보다 늘린 잘못 등재는 등급 격상뿐이다.
- **흔들림은 규칙이 아니라 원인에서 막아야 한다** — 제안만, 코드는 담당자 몫:
  (엔진·정기영) 경과 60분 전 드리프트를 억제하고 첫 1시간은 외기 보정을 하지 않으면 1시간 안 거짓 드리프트 태그가 34 → 2 로 준다. 60분 억제만으로는 근무 끝 결과가 안 바뀐다(표 6-라 「같음」). 반사실은 외기 보정을 근무 내내 끈 것이라 「짧은 창에서만 끔」의 1시간 이후·근무 끝 영향은 미검증이다.
  (app·박경모) 정지 확인 질문은 경과 N분(예: 60분) 전에는 묻지 않는다.
- **해소 규칙.** 「N틱 연속 안 보이면 해소」는 뒤집힘이 많다 — R2 등재 뒤 3틱 이상 비었다가 다시 뜬 것이 412회(10분 틱). 근무 중에는 지우지 말고 「관찰 끝(흐리게)」으로만 두고, 근무 끝 결과(= 배치, 1번)로 확정하는 쪽이 안전하다.
- **항목 동일성은 tag·kind 로 잡는다.** 시작 시각으로 잡으면 같은 드리프트가 여러 항목으로 쪼개진다(3번).

## 방법

- **배치 기준(공식 절차).** 세트마다 DB 하나: `bash tmp_live/batch.sh set1|set2|T|N` = `ENGRA_LLM=off` init → CSV 전부 ingest → 근무 시각순 run → `tools/score.py`.
  재현 확인: ① 22/22 · 이벤트 79 · 오탐 2(전부 복귀) · IoU 0.73 / ② 46/46 · 175 · 11(전부 복귀) · 0.69 — `docs/공식수치.md` ①② 와 같다. 알람 선행 최대만 다르다(① +616 vs 공식 +706, ② +560 vs +666 — 현재 main 엔진 값, 원인은 조사하지 않음).
  T 216 이벤트 · 21 항목, N 36 · 13 은 probe-ext 와 같다.
- **확장 근무.** probe-ext `tmp_probe_ext/T`(#29 팽창터빈 Trip, 2026-09-15-day) · `N`(#51~55 정상 5종, 2026-09-14-night)의 `shift.csv`·`answer_key.json` 을 `tmp_live/ext/` 로 복사만 했다(md5 동일). 그 폴더에는 쓰지 않았다.
- **틱.** 배치 DB 에서 근무 원본을 한 번 읽어 메모리에 두고, 틱 t 마다 태그별 `ts < t` 로 잘라(bisect) `ports.detect(잘린 원본, 배치가 그 근무 run 때 쓴 기준선)` → pipeline 과 같은 순서·id(detect 순 id, `ORDER BY start_ts, tag`)로 `ports.compose`(정지 질문 포함).
  **DB 에 다시 적재하지 않으므로 `collect.ingest` 의 같은 근무 원본 교체 문제가 생기지 않는다.** 과거 사례 검색은 빈 목록이다(배치 DB 에도 확정 일지가 없다).
- **틱 간격.** 10·5분(10근무, 5프로세스 병렬 — 흔들림·동등성) · 1분(① 주간). 계산 시간은 순차 실행(프로세스 1개)으로 따로 쟀다(① 주간 10·5·1분, T 10·5분). 다른 세션 부하(loadavg 3~12)가 섞였고 CPU 시간 ≈ 벽시계다.
- **추적 규칙.** 같은 tag·kind 이고 시작 시각이 직전 관측 시작 ±15분 안이면 같은 이벤트. 후보가 여럿이면 직전 틱에 있던 것 → 시작 차이 작은 것 순으로 1:1. 끊겼다 다시 뜬 것도 같은 규칙으로 잇고 「재등장」으로 센다.
  최종에 없는 추적의 분류: 태그째 없음 / 같은 태그 다른 종류만 / 한계선 등급 격상 / 같은 tag·kind 가 최종에 있음(시작 이동). 비교용으로 시작 조건을 뺀 「tag·kind 만」 규칙도 냈다(표 3-마).
- **등재 규칙.** R1 처음 뜬 틱 · R2 연속 2틱 · R3 연속 3틱 · R2+ = R2 이되 kind 에 초과·미달이 있으면 R1. 잘못 등재 = 근무 중 등재됐는데 최종(= 배치)에 없음. 지연 = 등재 틱 − 처음 뜬 틱.
- **시나리오 매칭**은 `tools/score.py` 와 같다(영향 태그 ∪ 트리거, 구간 겹침). 이월 꼬리(10분 미만 carried_in)는 뺐다.
- **알람 시각.** 정답지 `dcs_alarm` 에 적힌 (태그, 등급)의 원본 2초 값이 주입 시작 뒤 처음 한계(태그 마스터 H/HH 초과, L/LL 미달)를 넘은 시각. 여러 태그면 가장 이른 것.
- **AI 대기열.** 틱마다 「등재된 항목(묶음) 중 앞 틱 등재 항목과 멤버가 하나도 안 겹치는 것」이 신규 작업이다. 틱 k 의 작업은 실시간 k × 간격 × 0.6초에 도착하고, 작업자 8명이 작업당 45초씩 도착순으로 처리한다. 근무 끝 틱에 남은 항목은 전부 등재로 센다. 정지 질문은 뺐다. 45초·동시 8 은 지시받은 추정치다.
- **반사실(표 6-라).** `cf_probe.py` 가 **자기 프로세스 안에서만** `engine.core._apply_noise_model`(외기 보정) · `engine.detectors.SINGLE` 의 drift(블록 120개 미만이면 빈 목록)를 바꿔 끼웠다. 저장소 파일은 그대로다.

## 함정

1. **정지 질문이 모든 근무 첫 틱에 뜬다**(요약 5). 실시간 화면에 그대로 붙이면 근무 시작마다 「플랜트를 정지하셨습니까?」가 뜬다.
2. **±15분 추적은 드리프트 추적을 끊는다.** 드리프트 보고 구간의 시작은 CUSUM 좁히기와 「가장 이른 창」 선택 때문에 틱이 지나며 옮긴다(처음→마지막 최대 72분). 사라짐의 1/3(477/1,419)이 이것이다.
3. **대표 1건만 보고하는 검출기가 있다.** 순간 이탈은 근무 중 가장 큰 튐 1건만 낸다. ② 08-22 야간 LI-806 은 19:10 튐이 초안에 올랐다가, 더 큰 21:10 튐이 오자 사라졌다(최종엔 21:10). 한계선도 가장 심한 등급 1건만 내서 H 초과가 HH 초과로 바뀐다. 「사라짐」의 일부는 오탐이 아니라 대표 교체다.
4. **T 유령 드리프트(#36)는 Trip 뒤 약 25분(11:25)부터 뜨고 개수가 널뛴다** — 12:30 37건 → 14:00 9건 → 18:00 44건(드리프트 창 선택이 바뀔 때마다). 외기 보정을 끄면 0 이다 — 외기 보정이 원인임을 틱에서도 확인했다.
5. **「배치와 같은 기준선」 조건은 지켰지만 결과를 가르지 않는다**(요약 1).
6. 틱마다 DB 를 다시 읽는 구현이면 읽기(12시간 창 1.05초)가 검출(0.70초)보다 크다. 이 실험은 메모리에서 잘랐다.
7. 공식수치와 알람 선행 최대가 다르다(방법 첫 항목).
8. 계산 시간은 다른 세션 부하 속에서 쟀다(loadavg 3~12). 여유 판정 쪽으로는 보수적인 값이다.
9. 1분 틱의 알람 대비는 ① 주간 4건뿐이라 표에만 두고 요약에서 뺐다.
